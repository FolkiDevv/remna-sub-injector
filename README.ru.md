# remna-sub-injector

**Remnawave Subscription Injector Proxy** — добавляет дополнительные протоколы (Hysteria2, TrustTunnel, SOCKS, MTProto и др.) в единую подписку [Remnawave](https://docs.rw) без изменения upstream-сервера.

## Что делает

Когда VPN-клиент запрашивает список подписки, инжектор:

1. Пересылает запрос на upstream-сервер подписок без изменений
2. Проверяет заголовки запроса (например, `User-Agent`) по настроенным правилам
3. Если правило совпало и ответ является base64-закодированным списком подписки — декодирует его, добавляет настроенные дополнительные ссылки и перекодирует перед отправкой клиенту
4. Если ни одно правило не совпало или ответ является YAML/JSON конфигом — пропускает без изменений
5. Если ответ является служебным сообщением, а не рабочей подпиской — пропускает без изменений

Это позволяет добавлять дополнительные ссылки (например, собственные Hysteria2 или VLESS узлы) в списки подписок без модификации upstream-сервера, при этом избирательно — для каждого клиентского приложения свои ссылки.

## Как работает инъекция

- Тело ответа должно быть base64-закодированным списком прокси URI, по одному на строку
- Инжектор декодирует тело из base64, добавляет дополнительные ссылки в конец и перекодирует обратно
- YAML и JSON никогда не модифицируются (конфиги Clash/Sing-Box)
- Правила проверяются по порядку; побеждает первое совпавшее
- Одно правило может брать ссылки сразу из нескольких источников — они склеиваются в том
  порядке, в котором перечислены; ссылка, встретившаяся в нескольких источниках, добавляется один раз
- Каждый источник кешируется, поэтому обновление подписки клиентом не приводит к запросу всех
  источников (см. [Кеширование](#кеширование))
- Если недоступны или пусты все источники совпавшего правила, ответ передаётся без изменений

## Служебные сообщения

Когда пользователь деактивирован, срок его подписки истёк или исчерпан лимит трафика,
Remnawave всё равно отвечает base64-списком — но состоящим из ссылок-заглушек, у которых
статус записан в ремарке. Дописать к такому ответу дополнительные ссылки означало бы выдать
заблокированному пользователю рабочие узлы, поэтому инжектор распознаёт такие ответы и
проксирует их без изменений.

Распознавание опирается на два признака, которые формирует сам Remnawave, — их не нужно
настраивать, и никакая настройка панели не может их незаметно отключить:

- **Служебные хосты** — все записи в теле ведут на нероутируемый адрес (`0.0.0.0`,
  `127.0.0.1`, `::`, `::1`, `localhost`). Единственный признак, который ловит
  деактивированного пользователя с ещё не истёкшим сроком и неисчерпанным трафиком.
- **Заголовок ответа `subscription-userinfo`** — `expire` ненулевой и в прошлом, либо
  `total` ненулевой и `upload + download` его достиг. (`expire = 0` означает «бессрочно», а
  `total = 0` — «безлимитный трафик»; ни то, ни другое не является служебным состоянием.)

Проверка намеренно консервативна: запись, из которой не удалось прочитать хост, — например
`vmess://`, прячущая адрес внутри base64, — считается настоящим узлом, поэтому нестандартное
тело будет дополнено, а не молча пропущено.

Причина каждого пропуска пишется в лог, без значения самого заголовка:

```
[sub-injector] skipping injection: service message (service hosts)
[sub-injector] skipping injection: service message (userinfo: expired)
[sub-injector] skipping injection: service message (userinfo: traffic limit)
```

## Заметки по безопасности

- **Закройте порт от внешней сети.** Инжектор не имеет встроенной аутентификации — безопасность строится исключительно на секретности токена подписки в URL. Убедитесь, что порт 3020 недоступен снаружи (правило firewall или изолированная Docker-сеть).
- **TLS на самом инжекторе отсутствует.** Трафик между клиентом и инжектором передаётся по plain HTTP, поэтому токены и ссылки идут в открытом виде. Если клиенты подключаются через интернет, поставьте перед инжектором reverse proxy (nginx, Caddy и т.д.) с TLS-сертификатом.
- **Источник ссылок сам может быть секретом.** Если источник — это подписка другой панели, её путь и есть охраняющий её токен. Инжектор никогда не пишет этот путь в лог: удалённый источник попадает туда только схемой и хостом (`https://panel.example.com/...`), так же как уже обрезаются пути входящих запросов. Пути локальных файлов пишутся целиком — они не секретны.

## Установка

### Вариант 1 — Docker Compose (рекомендуется)

Образ публикуется в GitHub Container Registry и собирается сразу под
`linux/amd64` и `linux/arm64`:

```
ghcr.io/folkidevv/remna-sub-injector:latest
```

Теги соответствуют версии релиза: `latest`, `1.2.3`, `1.2`, `1`.

Контейнер работает от непривилегированного пользователя (UID/GID `10001`) и
ничего не пишет на диск, поэтому может запускаться в режиме read-only.
Убедитесь, что `config.toml` и файлы в `data/` доступны этому UID на чтение —
обычных прав `644` достаточно.

**Шаг 1.** Склонируйте репозиторий:

```bash
git clone https://github.com/itwormz/remna-sub-injector /opt/remna-sub-injector
cd /opt/remna-sub-injector
```

**Шаг 2.** Создайте конфиг:

```bash
cp config.toml.example config.toml
```

Отредактируйте `config.toml` под свои настройки перед запуском.

**Шаг 3.** Подготовьте источник дополнительных ссылок.

В каждом правиле `config.toml` есть поле `links_source` — инжектор читает из него прокси URI и добавляет их в каждый подходящий ответ подписки. В нём указывается один источник или список источников:

- **Локальный файл** — создайте файл и запишите по одному прокси URI на строку:
  ```bash
  mkdir -p data
  nano data/hysteria2-links.txt
  ```
- **Внешний URL** — адрес `https://`, который возвращает ссылки в том же формате (по одной на строку).
- **Другая подписка** — ссылка на подписку `https://`. Такие ссылки отдают base64-список; инжектор распознаёт это и декодирует его, так что узлы из другой панели подмешиваются как есть.

Подробности — в разделе [Формат источника ссылок](#формат-источника-ссылок).

**Шаг 4.** Создайте `docker-compose.yml`:

```bash
cp docker-compose.yml.example docker-compose.yml
```

**Шаг 5.** Запустите:

```bash
docker compose up -d
```

### Вариант 2 — Бинарный файл + systemd

Готовые бинарники публикуются в [GitHub Releases](../../releases):

| Файл | Архитектура |
|---|---|
| `sub-injector-linux-x86_64` | x86_64 (большинство серверов) |
| `sub-injector-linux-aarch64` | ARM64 (Raspberry Pi, AWS Graviton и др.) |

**Шаг 1.** Скачайте бинарник:

```bash
ARCH=$(uname -m)
case $ARCH in
  x86_64)  BINARY="sub-injector-linux-x86_64" ;;
  aarch64) BINARY="sub-injector-linux-aarch64" ;;
  *) echo "Unsupported architecture: $ARCH"; exit 1 ;;
esac
curl -L https://github.com/itwormz/remna-sub-injector/releases/latest/download/${BINARY} \
  -o /usr/local/bin/sub-injector
chmod +x /usr/local/bin/sub-injector
```

Чтобы установить конкретную версию, замените `latest/download` на `download/v0.1.0` в URL.

**Шаг 2.** Создайте конфиг:

```bash
mkdir -p /opt/remna-sub-injector
curl -L https://github.com/itwormz/remna-sub-injector/releases/latest/download/config.toml.example \
  -o /opt/remna-sub-injector/config.toml
```

Отредактируйте `/opt/remna-sub-injector/config.toml` под свои настройки перед запуском.

**Шаг 3.** Создайте файл сервиса:

```bash
cat > /etc/systemd/system/sub-injector.service << 'EOF'
[Unit]
Description=remna-sub-injector
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/sub-injector
Environment=CONFIG_FILE=/opt/remna-sub-injector/config.toml
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=multi-user.target
EOF
```

**Шаг 4.** Включите и запустите:

```bash
systemctl daemon-reload
systemctl enable --now sub-injector
systemctl status sub-injector
```

Просмотр логов:

```bash
journalctl -u sub-injector -f
```

## Конфигурация

Инжектор читает конфиг из TOML-файла. По умолчанию ищет `config.toml` в рабочей директории. Путь можно переопределить через переменную окружения `CONFIG_FILE`.

### Справочник по параметрам

| Ключ | Тип | Обязателен | По умолчанию | Описание |
|---|---|---|---|---|
| `upstream_url` | string | да | — | Базовый URL upstream-сервера подписок |
| `bind_addr` | string | нет | `0.0.0.0:3020` | Адрес и порт для прослушивания |
| `cache_ttl` | integer | нет | `300` | Секунд, в течение которых источник переиспользуется, если он не объявил интервал сам |
| `cache_max_stale` | integer | нет | `3600` | Секунд, в течение которых источник продолжает отдавать последний удачный ответ после неудачного обновления |
| `cache_respect_headers` | bool | нет | `true` | `false` — игнорировать заголовки источника и всегда брать `cache_ttl` |
| `source_headers` | таблица | нет | Happ-набор | Заголовки, с которыми инжектор запрашивает источник-ссылку (см. [Запрос к источнику ссылок](#запрос-к-источнику-ссылок)) |
| `injections` | массив | да | — | Список правил инъекции (см. ниже) |

Каждое правило `[[injections]]`:

| Ключ | Тип | Описание |
|---|---|---|
| `header` | string | Название заголовка запроса для проверки (без учёта регистра) |
| `contains` | массив строк | Список подстрок — правило срабатывает, если значение заголовка содержит **любую** из них (без учёта регистра) |
| `links_source` | string **или** массив строк | Откуда берутся дополнительные ссылки: путь к локальному файлу, `http(s)://` URL или `http(s)://` ссылка на подписку. Несколько источников склеиваются в указанном порядке |

### Пример конфига

```toml
upstream_url = "http://upstream:2096"
bind_addr = "0.0.0.0:3020"

[[injections]]
header = "User-Agent"
contains = ["hiddify", "happ", "nekobox", "nekoray", "sing-box", "v2rayng"]
links_source = "/data/hysteria2-links.txt"

[[injections]]
header = "User-Agent"
contains = ["clash.meta", "mihomo"]
links_source = "/data/clash-links.txt"

# Несколько источников в одном правиле:
# [[injections]]
# header = "User-Agent"
# contains = ["hiddify"]
# links_source = [
#   "/data/hysteria2-links.txt",
#   "https://example.com/my-extra-links.txt",
#   "https://another-panel.example.com/sub/YOUR-TOKEN",
# ]
```

## Формат источника ссылок

Источник ссылок содержит по одному прокси URI на строке:

```
hysteria2://password@1.2.3.4:443?obfs=salamander&obfs-password=secret#Мой-Узел-1
vless://uuid@5.6.7.8:443?security=tls#Мой-Узел-2
ss://base64encodedinfo@9.10.11.12:8388#Мой-Узел-3
```

Пустые строки и пробелы в начале/конце обрезаются автоматически.

Источником может быть и целая **base64-подписка** — в таком виде их отдают Remnawave, Marzban и
остальные. Формат распознаётся, а не настраивается: если в теле нет ни одной читаемой ссылки, оно
декодируется из base64 и разбирается заново. Поэтому ссылку на подписку другой панели можно
указать источником напрямую, и её узлы попадут в ответ.

### Валидация

Всё, что вернул источник, проверяется на то, что это список прокси URI (`scheme://…`), прежде чем
хоть что-то из этого уйдёт клиенту, — так HTML-страница ошибки, капча или обрезанное тело не
попадут в подписку. Что происходит с частично читаемым источником, зависит от его вида:

- **Локальный файл** пишется руками, поэтому нечитаемая строка считается опечаткой: она
  выбрасывается, в лог уходит предупреждение с их количеством, остальные узлы подмешиваются.
- **Удалённый источник** формируется машиной, поэтому строка, не являющаяся прокси URI, означает
  порчу ответа, а не опечатку — источник отбраковывается целиком, и вместо него используются его
  закешированные ссылки (см. [Кеширование](#кеширование)).

Источник, чья собственная подписка истекла, отключена или исчерпала трафик, тоже отбраковывается:
в его теле лежат заглушки на `0.0.0.0`, распознаваемые ровно так, как описано в разделе
[Служебные сообщения](#служебные-сообщения), а подмешивание таких заглушек выдало бы клиентам
мёртвые узлы.

## Кеширование

Без кеша каждое обновление подписки клиентом перечитывало бы все источники — чтение файла и
полноценный HTTP-запрос чужой подписки на каждый запрос. Вместо этого каждый источник обновляется
по собственному расписанию.

**Локальные файлы** вообще не привязаны к таймеру. Они проверяются по времени изменения и размеру,
что дёшево, поэтому правка файла со ссылками применяется на следующем же запросе.

**Удалённые источники** обновляются с интервалом, который берётся из первого подходящего источника
данных:

1. **`profile-update-interval`** — заголовок ответа из
   [XTLS Subscription Standards](https://github.com/XTLS/Xray-core/discussions/4877), значение —
   **в часах**. Именно на него ориентируются сами VPN-клиенты; Remnawave его отдаёт (параметр
   `SUB_UPDATE_INTERVAL`, по умолчанию 12 часов), как и Marzban, Marzneshin и Hiddify Manager.
2. **`Cache-Control: max-age` / `s-maxage`** — в стандарт подписок не входит, но именно его
   отдаёт nginx или CDN, когда plain-text список раздаётся статикой. `no-cache` и `no-store`
   трактуются как «настолько часто, насколько разрешено», а не «на каждый запрос».
3. **`cache_ttl`** из конфига, по умолчанию 300 секунд.

Результат зажимается в диапазон от 30 секунд до 24 часов, чтобы ни слишком нетерпеливый источник,
ни случайный `profile-update-interval: 8760` не задавали правила. `cache_respect_headers = false`
пропускает шаги 1 и 2 и всегда использует `cache_ttl`. Если источник присылает `ETag` или
`Last-Modified`, обновление идёт условным запросом, и `304` просто перезапускает интервал.

`Expires` не поддерживается — в стандарте подписок он не используется, а разбор HTTP-дат означал
бы ещё одну зависимость.

Когда обновление не удалось — источник лежит, ответил не-2xx или вернул то, что не проходит
валидацию, — его последний удачный ответ продолжает отдаваться ещё `cache_max_stale` (по умолчанию
час) сверх интервала обновления. Дальше ссылки слишком старые, чтобы за них ручаться, и источник
выпадает из ответа. В обоих случаях остальные источники правила не страдают, а в логе видно, какой
источник протух. Это важно потому, что альтернатива молчалива: до кеширования упавший источник
означал, что клиент просто получал подписку без ваших дополнительных узлов.

## Запрос к источнику ссылок

Источник-ссылка (`http(s)://`) — это обычно другая панель подписок, а панель отвечает исходя из
того, кто спрашивает: формат ответа выбирается по `User-Agent`, а при включённом
[HWID-лимите](https://docs.rw/docs/features/hwid-device-limit/) панель ждёт `x-hwid`, без него
подписку она может и не отдать. Поэтому инжектор ходит за источником так, как это делает клиент
Happ:

| Заголовок | По умолчанию |
|---|---|
| `user-agent` | `Happ/2.0.0 (com.happproxy; iOS 18.3.0)` |
| `accept` | `*/*` |
| `x-hwid` | выводится из `upstream_url`, в формате UUID |
| `x-device-os` | `iOS` |
| `x-ver-os` | `18.3` |
| `x-device-model` | `iPhone` |

Это заголовки **самого инжектора**, а не клиента. Ничего из запроса, который вызвал обращение к
источнику, туда не пробрасывается — ни `User-Agent`, ни `x-hwid`, ни куки, — так что источник
видит одно постоянное устройство, а его ответ можно кешировать для всех, а не подстраивать под
того клиента, который пришёл первым.

`x-hwid` не генерируется случайно, а выводится из `upstream_url` — значение не меняется между
перезапусками и обновлениями, поэтому панель с лимитом устройств считает инжектор одним
устройством, а не новым после каждого деплоя.

Любой заголовок переопределяется таблицей `[source_headers]` — например, чтобы вписать точный
`User-Agent` своей сборки Happ или свой идентификатор устройства. Пустое значение убирает
заголовок совсем:

```toml
[source_headers]
user-agent = "Happ/2.5.0 (com.happproxy; iOS 18.3.0)"
x-device-model = ""
```

`[source_headers]` — обычная TOML-таблица, поэтому её нужно ставить **до** первого блока
`[[injections]]`, иначе TOML вложит её внутрь этого правила. Заголовки, которыми управляет сам
инжектор, отклоняются на старте: `if-none-match` и `if-modified-since` (валидаторы кеша),
`accept-encoding` (заданный вручную, он отключает автоматическую распаковку ответа), `host`,
`content-length` и hop-by-hop-заголовки.

К файловым источникам ничего из этого не относится — они читаются с диска.

## Сборка из исходников

Нативный бинарник (x86_64):

```bash
cargo build --release
```

ARM64 musl (для Alpine / серверов на aarch64):

Установите инструмент кросс-компиляции один раз:

```bash
cargo install cross
```

Затем выполните сборку:

```bash
cross build --release --target aarch64-unknown-linux-musl
```

Результат: `target/aarch64-unknown-linux-musl/release/sub-injector`

### Docker-образ

`Dockerfile` многоэтапный — он сам компилирует бинарник, заранее собранный
артефакт не нужен:

```bash
docker build -t sub-injector .
```

На выходе — образ на базе `scratch`, содержащий только статически слинкованный
бинарник (несколько мегабайт).
